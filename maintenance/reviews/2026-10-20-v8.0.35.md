## Integration findings

### Snapshot guards and the new watcher code complement one another

Upstream `7484a521` keeps file-backed credentials indexed while a scan encounters incomplete JSON. It preserves concurrent observations and pending provider reloads instead of issuing an accidental deletion. See `internal/watcher/dispatcher.go:145-283` and `internal/watcher/clients.go:85-182`.

That does not replace either fork fence. The canonical bound-file digest rejects a complete but obsolete file snapshot. The save/observation timestamp also protects an unbound/store snapshot. Both checks still execute under the per-auth mutation gate in `sdk/cliproxy/auth/conductor_lifecycle.go:310-339`. Incremental file snapshots remain stamped before the read in `internal/watcher/clients.go:215-220`.

The config fence is also separate. `internal/watcher/config_reload.go:57-89` parses the exact bytes it hashed, while SourceHash rejects an older loaded config after a management save. The new upstream auth/watcher logic does not provide that config guarantee. Dropping either patch because the watcher changed would reopen an unrelated race.

### Safe Modify preserves the latest credentials and the fork's save marker

Upstream `d69962e4` replaces stale read-edit-Update handling in the management fields/status paths with a callback applied to the latest clone under the per-auth gate. It checks registration epoch before editing, commits through `updateInternalLocked`, then releases the gate before hooks and scheduler publication. See `sdk/cliproxy/auth/conductor_lifecycle.go:214-254` and `internal/api/handlers/management/auth_files_fields.go:129,335`.

This path still reaches the fork's ordinary persistence wrapper, so it advances the save marker used by UpdateFromSnapshot. It does not need to be rewritten into snapshot mode. Concurrent fields PATCH, refresh and registration replacement cases pass their upstream regressions in the merged candidate.

### Codex refresh changes improve rejection recovery without changing binding policy

Upstream `feb63984` advances the normal Codex outer-token refresh lead from 24 to 96 hours and tracks a token rejected with 401 even when its JWT has a future expiry. A later background refresh can recover it after a transient request-time refresh failure. In-stream 401 handling now invalidates sibling model shards at credential scope and schedules refresh.

The manager still rejects results from an older credential version/registration before mutating the current auth in `sdk/cliproxy/auth/conductor_cooldown.go:859-902`. Request-time rejected-token marking also compares the exact failed token with the current token in `sdk/cliproxy/auth/conductor_refresh.go:790-805`. The new scheduler credential predicate matches the legacy selector's existing unauthorized/expired-token exclusions. I found no new reason for a valid healthy binding to move.

The custom nearest-reset hook remains outside Manager.mu and the affinity pick lock. It skips usage lookup for a healthy binding and re-gathers eligibility after a lookup. See `sdk/cliproxy/auth/conductor_quota_selection.go:13-44` and the call sites in `conductor_selection.go`. Upstream's plugin scheduler snapshot refactor does not bypass those calls. Actual OAuth rotation is not proven by these synthetic checks.

### One nonblocking SIWC consistency gap

The new explicit `BindCodexSIWC` API writes through `codex.WriteJSONFileAtomic` and publishes directly in `sdk/cliproxy/auth/codex_siwc_bind.go:95-160`. It bypasses `persist()` and therefore does not advance the fork's `lastSavedAt` marker at `conductor_lifecycle.go:745-760`.

At the manager API level, a previously captured unbound Generation=0 snapshot can therefore pass the old timestamp fence after binding and replace the new SIWC state. This is a code-path inference, not a reproduced production failure. Normal file watcher snapshots remain protected by their bound digest. Both builtin and plugin file synthesis bind that digest, SIWC binding requires an explicit management action, and the normal store Load occurs during startup before the management server is available. I did not find an active unbound snapshot path concurrent with SIWC binding in this service.

Classify this as bounded API hardening, not a fleet upgrade blocker. If we later support unbound live snapshots alongside SIWC binding, mark the successful direct local write under the existing gate and add one stale-unbound/fresh-snapshot regression. There is no reason to introduce new storage or synchronization infrastructure for it.

### Keep the remaining SSE and compaction corrections

The complete SSE parser equivalent to the old PR6708 work is already upstream from v33. Do not reintroduce the interim parser. The remaining fork validation requires buffered nonstream SSE to include message_stop. That is still a real difference at `internal/runtime/executor/claude_executor_stream.go:556-608`, backed by strict completion regressions.

PR6716 remains semantically needed. `claudeCodeContextManagementFits` prevents CPA from injecting context_management into top-level on-demand compaction. The Codex Responses translator preserves the supported compaction-only array while discarding other context_management shapes. See `claude_executor_cloaking.go:1513-1568` and `internal/translator/codex/openai/responses/codex_openai-responses_request.go:256-287`.

V35's shared compaction helper and Kimi/Meta capsule support serve different paths. They do not implement or supersede these native Claude/Codex corrections. Natural provider compaction remains unproven by the synthetic request-shape regressions.

### New search restoration respects payload rules; native Claude stays outside its scope

The Claude web-search result cache is disabled by default and applies only to Responses-format requests translated to Claude. `claude_executor.go:192-204` enforces both conditions. The new restore operations run before final user payload rules in execute, stream and token-count paths. The final filter test passes, so restoration does not reinsert content after a user's payload filter.

The new Codex web_search_call reconciliation and reasoning-signature cleanup also run before the existing HTTP/WebSocket final payload barrier. Tests pass for replayed search history, image filtering and SIWC compact finalization. The new uncloak policy is explicit; unchanged native OAuth/settings do not automatically opt into it. No new cache or cloak setting should be enabled merely because the code is present.

### Ledger and persistence format remain separate from these upstream additions

The ledger bridge still registers its three GET paths behind the existing v8 management middleware. It remains optional, uses a fixed literal loopback origin, and adds no inference dependency. Its access/forwarding/failure tests pass. The new SIWC v8 routes do not collide with it.

The durable affinity files and schema-1 implementation are unchanged by the upstream delta. That supports retaining current checkpoint bytes and software rollback compatibility at the source level. It is not a Windows artifact or rollback drill result.
